# ScenarioProposal и ScenarioResult
Proposal: scenario_id, baseline_analysis_id, operation_type, fixed_parameters, evidence_refs, assumptions, status=proposed. Операции формирует сервер из allowlist. UI передаёт scenario_id, а не произвольную правку расписания.
Проверка только по «Проверить сценарий». Вход run: scenario_id и immutable baseline. Результат: before/after raw metrics, worsened effects, affected_population либо affected_sites, versions. Индексные delta рассчитываются engine по FORMULAS.md только при сопоставимых численных before/after; иначе null с причиной.
Согласование пересадки — базовый сценарий. Дополнительное отправление требует подтверждения потребности и исполнимого расчёта. Нельзя просто вычитать минуты из внешнего маршрута. Эффект до запуска не заявляется.

Сохранять feasibility=verified|unverified, изменённые service_ids, shift_seconds, ресурсные ограничения. При отсутствии оборота — только модельный эксперимент; не подтверждённое предложение внедрения. baseline версии заморожены; scenario получает новый graph overlay. Повторный запуск идемпотентен.

### Грузовая обработка: additive расширение v2, 2026-11-11

`operation_type=reduce_handling_wait` — отдельная серверная операция для
`intercity_cargo` с `cargo_transport=multimodal`. Она меняет длительность
существующей обязательной `CargoAction(kind=handling)` и повторно запускает
публичный engine на полном графе: расписание следующего плеча может поглотить
выигрыш, поэтому фиксированная разница до запуска не заявляется.

`fixed_parameters.handling_changes` содержит `action_id`, `before_seconds`,
`after_seconds`, `resource_id`, `resource_units_before`, `resource_units_after`,
`valid_from`, `valid_to`. Требуются положительное сокращение, добавленный ресурс,
доказательства спроса и ресурса, подтверждённая совместимость действия, совпадение
исходной длительности и окно ресурса, покрывающее реальные интервалы engine.
В приватной hash-pinned `CargoScenarioDocument.resources` обязательно присутствует
факт с `resource_id`, точным `cargo_profile_id`, `compatible_action_ids`,
`available_units`, `valid_from`, `valid_to`, `evidence_refs`. Идентификатор ресурса,
действие и профиль совпадают точно; заявленные единицы не превышают доступные,
окно изменения и реальные интервалы before/after входят в окно факта. Evidence
факта входит в resource evidence плана и в проверенные записи канонического
snapshot. Неизвестный ресурс, отсутствие факта, недостаточная ёмкость или
несовместимость приводят к отказу, а не `verified`.

Это **предложение BACKEND по интерфейсу ресурса**, предметное согласование
Матвеем и Максимом ещё требуется. `after_seconds` остаётся фиксированным
модельным условием versioned документа: зависимости «число единиц → скорость
обработки» backend не вычисляет. Результат содержит ограничения
`MODELLED_CARGO_PROCESSING_RESOURCE` и
`CARGO_RESOURCE_CONTRACT_PENDING_APPROVAL`; проверка заданного модельного ресурса
не подтверждает готовность реальных ML2 данных или внедряемость операции.
Для этой операции `service_ids=[]`, `shift_seconds=0`, `turnaround_evidence=[]`:
обработка не представляется сдвигом рейса. В `ScenarioResult` сохраняется точно
такой же массив `handling_changes`, а `service_changes=[]`.

Пустые `handling_changes` не сериализуются, поэтому старые предложения и
результаты операций расписания сохраняют прежний JSON. Потребителям необходимо
добавить новое значение enum и отображение фиксированных изменений обработки.
Общий endpoint и body запуска не меняются: POST `/scenarios/{scenario_id}/runs`
с `{"schema_version":"2"}` и `Idempotency-Key`.

Городской `urban_cargo` engine сейчас считает время доступа грузовика и не
принимает обработку/ожидание в узле. Такая операция отклоняется с
`CARGO_HANDLING_MODEL_UNAVAILABLE`; её нельзя подменять изменением дорожного
времени или фиктивной межгородской парой.
`intercity_cargo` с `cargo_transport=pipeline` также не принимает эту операцию:
repository отклоняет предложение/эффект до публикации. Поддержка ограничена
настоящим `IntercityCargoRequest` с `cargo_transport=multimodal`.

### Полнота сопоставления и изменения связности

Каждая исходная задача времени/индекса остаётся представленной в `after`, даже при потере связи. Удалять показатель или заменять задачу под прежним ID нельзя: stable IDs закрепляют пару, переименованные IDs требуют однозначной семантики либо явной связи эффекта. Идентичность задачи включает subject (территория/пара/режим/категория), единицу, тип времени и основания агрегирования; journey ID может меняться при сохранении задачи. Неизменившийся показатель не требует нулевого эффекта.

- Подтверждённое появление связи: `outcome=new_connection`, `delta=null`.
- Подтверждённая потеря связи: **`outcome=lost_connection`**, `delta=null`; raw Metric ID в `after` входит в `worsened_metric_ids`. Это additive расширение enum v2, потребители должны отображать событие потери отдельно от числовой экономии.
- Для отсутствовавшего/утраченного пути требуется полный scoped placeholder: Metric `status=not_applicable`, `value=null`, `reason_code=NO_FEASIBLE_ROUTE`, evidence в source_refs; либо подтверждённый ноль Score с таким reason/evidence. Для существующего пути — available/full. Unknown не доказывает отсутствие пути.
- `available→unknown` и `unknown→available` требуют явного `unknown` эффекта и `partial` результата, без выдуманной разницы или доказанного события связности. Несопоставимая семантика/единицы также требуют явного unknown и partial. Полностью успешный результат не скрывает такие переходы.

Хранилище сверяет `before` с immutable baseline; worker и repository повторно валидируют результат перед публикацией. Исторические payload без новых событий остаются wire-совместимыми, если соблюдают эти инварианты. Ранее сохранённый противоречивый payload (удалённая задача, скрытая потеря/смена смысла) при повторной загрузке отклоняется валидацией; backend не дописывает события и числа задним числом. Для таких данных нужен отдельный пересчёт, а не молчаливая переинтерпретация.
