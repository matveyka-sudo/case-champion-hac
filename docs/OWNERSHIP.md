# Владельцы и передача изменений

| Роль | Сессия | Ветка | Пути и ответственность |
| --- | --- | --- | --- |
| №1 FRONTEND | Codex | `work/frontend` | `apps/web/**`, `docs/tasks/frontend.md`. SPA, карта, клиентские типы и проверки, `package.json` и `package-lock.json`. |
| №2 DEVOPS | Codex | `work/devops` | `infra/**`, `.github/**`, файлы корня, `artifacts/**`, общие `docs/**` с исключением ниже. Все `pyproject.toml` и единственный `uv.lock`. |
| №3 BACKEND | Codex | `work/backend` | `apps/api/**`, `packages/contracts/**`, `contracts/generated/**`, `packages/assistant/**`, `docs/tasks/backend.md`. HTTP, jobs, БД, миграции, DTO, OpenAPI, инструменты и агент. |
| №4 ML1 | Codex | `work/ml1` | `packages/engine/**`, `docs/tasks/ml1.md`. Детерминированная маршрутизация, индекс, сценарии и профиль расчёта. |
| №5 ML2 | Claude Code | `work/ml2` | `packages/data_pipeline/**`, `data/**`, `ml/**`, `docs/tasks/ml2.md`. Источники, учреждения и услуги, география, календари, QA и evidence. |

Правила разрешения пересечений

1. Любой `pyproject.toml` и корневой `uv.lock` принадлежат DEVOPS, включая файлы внутри чужого модуля. Установка нового npm-пакета и изменение npm lock принадлежат FRONTEND.
2. Каждый `docs/tasks/<role>.md` принадлежит этой роли, включая `docs/tasks/devops.md`. Локальная документация принадлежит владельцу модуля. Общая архитектура и справочные материалы принадлежат DEVOPS с согласованием предметного содержания. BACKEND утверждает общие схемы, ML1 согласует семантику транспорта, ML2 согласует схему входных данных и evidence.
3. Для БД роль использует отдельный Compose-проект с уникальным портом или изолированную тестовую БД/схему. Владелец схемы или lock-файла готовит изменение. Согласованное изменение в `dev` принимает координатор интеграции.

Передача `packages/assistant` по ТЗ 1.1, с. 7, 11–13. BACKEND принимает агент, инструменты и их evals. ML2 передаёт принятые данные, evidence, ручную сверку и известные пробелы. На момент корректировки в модуле только структура и manifest. Будущую или неинтегрированную работу согласуют отдельным handoff по коммиту, путям, статусу и критериям.

## Ветки и PR

`main` — основная ветка проверенных версий и готовых демонстраций. `dev` — общая ветка интеграции. У координатора свой checkout `dev`, у каждой роли свой checkout ветки из таблицы. На общей машине используйте отдельные worktree. Участники на разных компьютерах клонируют репозиторий и выбирают свою опубликованную ветку. Локальные worktree существуют только на машине, где их создали. У каждого checkout свои `.env`, `.venv` и `node_modules`.

1. Перед работой проверьте текущую ветку, `git status`, корневой и применимые локальные `AGENTS.md` и существующую реализацию. Меняйте файлы своей области.
2. Выполните проверки изменённой области, сделайте небольшой связный коммит и отправьте свою ветку обычным push.
3. Откройте PR из своей `work/<role>` с базой `dev`. Укажите результат, влияние на контракты, выполненные проверки и их исход.
4. Назначенный координатор интегрирует согласованные PR в `dev` с merge-коммитом и сохраняет рабочие ветки. Для этого на GitHub должны быть разрешены merge-коммиты и отключено автоматическое удаление веток. После проверки общего результата координатор открывает PR из `dev` в `main`.
5. Перед следующим блоком работы проверьте чистоту своего checkout. Сначала обновите рабочую ветку из её upstream только fast-forward, затем влейте согласованные изменения `origin/dev` обычным merge. Получение этих изменений разрешено для всех ролей. Если fast-forward невозможен или возник конфликт в чужом модуле, согласуйте решение с координатором и владельцем затронутого модуля.

```bash
git fetch origin &&
  git merge --ff-only '@{upstream}' &&
  git merge origin/dev
```

Постоянные ветки сохраняют общую историю. Для интеграции используется merge, а переписывание истории, force push и повторное squash-слияние исключены из рабочего процесса.

## Передача изменений между ролями

В handoff укажите путь, причину, необходимые поля или поведение, критерий приёмки и ссылку на коммит или результат проверки. Например, ML1 передаёт BACKEND запрос на поле причины в `JourneyResult`, объясняет область покрытия и перечисляет статусы для проверки. Сообщение передаётся через участника команды или в согласованном месте репозитория.
